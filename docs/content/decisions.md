## D-01 콘텐츠 DB 배포 라이선스 — 결정(2026-11-01, 사용자)

- JMdict·KANJIDIC2(CC BY-SA) 기반 데이터와 거기서 파생한 한국어 뜻을 포함한 콘텐츠 DB는 **CC BY-SA로 공개 배포**한다. 버전은 원 자료와 호환되는 버전으로 한다. 구체 버전과 각 자료(KanjiVG, Tatoeba 등)와의 호환 여부는 `sources.md`에서 원 출처·라이선스 전문으로 확인해 적는다(확인 전에는 미확인).
- **앱 코드는 콘텐츠 DB 파일과 분리**해 별도 라이선스로 둔다(D-05). 파이프라인 산출물(DB 파일)과 앱 소스는 서로 다른 파일·경로로 두고, 저작자 표시 화면과 DB 배포물에 DB의 라이선스를 따로 밝힌다.
- 적용: 저작자 표시 화면(`content-licensing` 5절)에 콘텐츠 DB 라이선스 이름·링크, 원 자료별 출처, 앱이 가한 변경(급수 필터, 한국어 뜻 추가 등)을 표시한다.

## D-02 한국어 뜻 생성 방식 — 결정(2026-11-01, 사용자)

- 한국어 뜻은 **JMdict 영어 뜻을 참고·번역해 만들어도 된다**(`content-licensing` 4절 방식 A 허용). 직접 집필(방식 B)과 함께 쓸 수 있다.
- 이렇게 만든 뜻은 **JMdict의 파생물**로 취급한다. 콘텐츠 DB와 함께 D-01 라이선스로 배포하고, 출처(JMdict/EDRDG)와 변경 사실("영어 뜻을 바탕으로 한국어로 번역")을 표기한다.
- 행마다 뜻 출처·생성 방법(예: `llm:<모델>@<날짜>`)·검수 상태를 남기는 규칙(`content-licensing` 4절)은 그대로다.
- 다른 사전의 한국어 뜻풀이를 옮기지 않는다. 방식 C(일한 대역 자료)는 해당 자료의 라이선스가 확인되면 따로 검토한다.

## D-03 한국어 뜻 검수 수준 — 미정

누가 검수하느냐에 따라 비용과 신뢰도가 크게 다르다. 하네스의 `jlpt-content-author`는 LLM 에이전트이므로, 그 검수는 "사람 검수"가 아니다. 화면의 검수 상태 표시는 이 구분을 따라야 한다.

| 선택지 | 내용 | 장점 | 비용·위험 |
|--------|------|------|-----------|
| A. 전수 검수 | 번들하는 모든 뜻을 검수 | 오역이 학습자에게 가는 경우가 가장 적다 | 항목 수에 비례(급수 목록 확정 후 항목 수로 산정, 현재 미산정). 사람이 하면 가장 비싸다 |
| B. 표본 검수 | 묶음마다 일정 비율(예: 5~10%)을 뽑아 검수, 오류율이 기준을 넘으면 묶음 전체를 다시 생성·검수 | 비용이 작다 | 표본 밖 오역은 그대로 배포된다. 미검수 행을 화면에서 구분 표시해야 한다 |
| C. 혼합 | 하위 급수(N5·N4) 또는 고빈도 항목은 전수, 나머지는 표본 | 초급 학습자가 먼저 보는 뜻의 품질을 확보 | 기준(급수·빈도)을 정해야 한다 |
| 검수자 축 | ① 에이전트(LLM) 검수 ② 사람(한국어 화자, 일본어 가능) 검수 ③ ①로 거른 뒤 ②가 표본 확인 | ①은 빠르고 싸다 | ①만으로는 같은 계열 모델의 오류를 놓칠 수 있다. ②는 사람 시간이 든다 |

**보수적 기본값 제안(확정 아님):** 첫 콘텐츠 마일스톤은 N5만 번들 대상으로 하고, N5 뜻을 에이전트가 전수 검수한다. 행마다 `reviewStatus`(`unreviewed`/`sampled`/`reviewed`)와 검수자 종류(에이전트/사람)를 남기고, 사람이 검수하지 않은 뜻은 화면에서 그 사실을 알린다. 사람 검수 범위는 사용자가 정한다.

## D-04 청해 음성 방식 — 미정

청해는 계획상 4순위(MVP 밖)라 첫 마일스톤에는 이 결정이 필요 없다. 녹음 음성(시험·교재 음원, Tatoeba 음성 등)은 어느 경우에도 쓰지 않는다(`content-licensing` 1절).

| 선택지 | 내용 | 장점 | 비용·위험 |
|--------|------|------|-----------|
| A. 기기 TTS(ja-JP) | 앱 실행 중 Android `TextToSpeech`로 합성 | 추가 비용 없음, 에셋 크기 증가 없음, 대본만 고치면 바로 반영, 음성 파일을 배포하지 않으므로 음성 파일의 라이선스 문제가 없다 | 기기·엔진마다 음질·읽기가 다르다. 일본어 음성 데이터가 없는 기기가 있어 설치 안내가 필요하다. 읽기 오류는 대본의 `ttsText` 힌트로만 막을 수 있고, 실기기에서만 확인된다 |
| B. 사전 생성 음성 | 파이프라인에서 TTS 엔진으로 음성 파일을 만들어 번들 | 모든 기기에서 같은 소리, 배포 전에 읽기 오류를 듣고 고칠 수 있다, 일본어 음성 없는 기기에서도 동작 | 엔진 선택과 그 이용 조건(생성 음성의 재배포·상업 이용·크레딧 표기, 음성 파일에 붙일 라이선스와 D-01의 호환)을 원 출처로 확인해야 한다 — **엔진별 조건은 미확인**. 에셋 크기 증가(대본 수 × 길이, 미산정). 대본을 고칠 때마다 다시 생성해야 한다 |
| C. A로 시작, B 추가 가능 | 재생을 `Speaker` 인터페이스 뒤에 두고 A로 구현, B는 나중에 같은 인터페이스로 추가 | 지금 결정을 미루면서 나중 비용을 줄인다 | 두 구현을 함께 유지할 수 있다 |

**보수적 기본값 제안(확정 아님):** C. 청해 마일스톤 전까지 결정을 미루고, 설계에서는 재생을 `Speaker` 인터페이스 뒤에 둔다. B를 고르면 그때 엔진 후보를 1단계(`license-verify`)에 넣어 확인한다.

## D-06 급수 목록 자료 선택 — 미정

`sources.md`에서 라이선스가 확인된 후보 중에서 고른다. 1단계 결과와 함께 선택지를 올린다.

## D-07 EDRDG 데이터 갱신 주기 — 미정

EDRDG 라이선스는 데이터를 포함한 앱에 최신판으로 정기 갱신하는 절차를 요구한다(`sources.md` S-01.update, 확정). 주기는 라이선스가 정하지 않는다(월 1회는 WWW 서버 예시). 오프라인 번들 앱이므로 앱·DB 업데이트 배포 주기로 충족해야 한다. 선택지: 앱 출시마다 / 정해진 주기(예: 분기) / 공개 배포 시작 시 정함. 설계에서는 파이프라인이 최신판을 받아 다시 만들 수 있게(체크섬·판 기록) 하는 것으로 충분하다.

## D-08 급수 목록·Tatoeba 스냅샷을 공개 저장소에 커밋할지 — 미정

architecture.md 6.7은 원본 판을 `content/snapshot/`에 커밋한 스냅샷으로 고정한다. S-01·S-02·S-03 스냅샷은 architecture가 이미 정했다(CC BY-SA, `sources.md` S-01.pinning·S-02.pinning·S-03.pinning). 이 항목은 남은 두 종류만 다룬다.

- `levels-<levelSource>-<version>.tsv`: 고른 급수 목록(D-06)의 **모든 급수** 행. 첫 DB가 N5만 번들해도 스냅샷에는 N5~N1이 다 들어간다.
- `S-04-<version>.jsonl.gz`: DB에 넣는 Tatoeba 문장 행만(id, lang, text, username, 문장별 라이선스, jpn–kor 연결). 예문을 처음 쓰는 마일스톤(지금 마일스톤 목록에는 없음)에서 만든다.

판단 전제(확인한 사실):

1. 공개 콘텐츠 DB(D-01)에도 급수(`level_source_id`, architecture.md 4절)와 쓰인 문장이 들어간다. 스냅샷 커밋은 같은 자료를 다른 형태로 다시 배포하는 것이다. 급수 목록 스냅샷은 DB보다 범위가 넓을 수 있다(위).
2. 방식 B(`archive`, 저장소 릴리스 첨부 등 공개 URL)도 공개 배포다. 붙는 의무는 커밋과 같다. 차이는 되돌리기다. 릴리스 첨부는 지울 수 있지만, 커밋은 히스토리를 다시 써야 지워지고 이미 받아 간 복제본에는 남는다.
3. 이 저장소에는 아직 원격(remote)이 없다(2026-11-02 `git remote -v` 결과 없음). 공개 시점은 AR-U07에 따른다.
