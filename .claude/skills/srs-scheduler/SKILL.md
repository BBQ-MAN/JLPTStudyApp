# SRS Scheduler — 간격 반복 스케줄러 규칙

스케줄러가 틀리면 앱은 테스트를 모두 통과한 채 사용자가 외운 단어를 너무 늦게, 또는 너무 자주 보여 준다. 사용자는 몇 주 뒤에야 "외운 게 안 남는다"로 알아챈다. 그래서 알고리즘은 근거로 고르고, 구현은 참조 값으로 고정하고, 모든 기록을 남겨 나중에 고칠 수 있게 한다.

## 1. 알고리즘 선택(설계 단계, android-architect)

FSRS 계열(예: FSRS-5/6)과 SM-2 계열(SM-2, 그 변형) 가운데 하나를 아래 기준으로 비교해 `architecture.md`에 결정과 근거를 적는다. 판 번호, 기본 파라미터, 벤치마크 수치, 라이선스는 기억으로 적지 않는다. 원 출처(알고리즘 공식 문서·저장소, 공개 벤치마크, 라이선스 파일)를 열어 링크와 확인 날짜를 남긴다.

| 기준 | 확인할 것 |
|------|-----------|
| 기억 예측 정확도 | 공개 벤치마크(예: open-spaced-repetition의 srs-benchmark)에서 두 계열의 지표와 데이터 규모 |
| 기본값만으로 쓸 수 있는가 | 복습 기록이 없는 새 사용자에게 기본 파라미터로 충분한지, 파라미터 최적화를 기기에서 해야 하는지 |
| 구현·검증 난도 | 상태 변수 수, 부동소수 계산, 참조 구현과 테스트 벡터 존재 여부 |
| 참조 구현 라이선스 | 이식하거나 테스트 벡터를 가져올 참조 구현의 라이선스와 그 의무(저작권 표시 등) |
| 평가 버튼 수 | 사용자가 매 카드에서 고르는 단계 수(FSRS 4단계, SM-2 원형 0~5 6단계)와 화면 설계 영향 |
| 저장 상태 | 카드마다 저장할 값, 나중에 알고리즘을 바꿀 때 복습 로그로 다시 계산할 수 있는지 |

결정이 갈리면 두 안의 장단점과 추천을 사용자 승인 항목으로 올린다.

## 2. 모듈 계약(`:core:srs`)

- 순수 함수 또는 불변 상태 기계: `schedule(card: CardState, rating: Rating, reviewedAt: Instant, config: SrsConfig): ScheduleResult`. 결과에는 새 상태, 다음 기한(`dueAt`), 평가별 다음 간격 미리보기를 담는다.
- Android, Room, 시스템 시계에 의존하지 않는다. 시각은 인자로만 받는다.
- 난수(간격 흩뿌리기)를 쓰면 시드를 카드 ID와 복습 횟수로 정해 결정적으로 만든다. 같은 입력이면 항상 같은 결과가 나와야 테스트와 되돌리기가 성립한다.
- 상태는 직렬화할 수 있는 값만 담는다(`data class`, 기본 타입). Room 엔티티로의 변환은 `:app`이 한다.
- 알고리즘 판을 `schedulerVersion`으로 드러낸다. 저장된 상태가 어느 판으로 계산됐는지 알아야 교체할 수 있다.

## 3. 시간과 학습일

- 저장·계산 시각은 UTC `Instant`(epoch ms). "오늘 복습할 카드"는 사용자 시간대(`ZoneId`)와 학습일 경계 시각(기본 04:00, 설정 가능)으로 정한다. 새벽 1시에 공부한 카드가 "어제"로 계산되도록 하기 위해서다.
- 일 단위 간격은 학습일 기준으로 센다. 학습 단계(분 단위 재학습)와 일 단위 간격을 섞을 때 경계 규칙을 명시한다.
- 기한보다 늦게 복습한 경우(연체)와 일찍 복습한 경우를 알고리즘 정의대로 처리하고 테스트한다.
- 최대 간격 상한을 둔다(설정값).

## 4. 테스트 우선 절차

1. 계약 시그니처와 실패하는 테스트를 먼저 쓴다. `:core:srs:test`가 실패하는 것을 확인한다.
2. 구현해 통과시킨다. 테스트를 구현에 맞춰 고치지 않는다. 테스트가 틀렸다고 판단하면 근거를 보고서에 적는다.
3. 테스트 묶음:

| 묶음 | 내용 |
|------|------|
| 참조 벡터 | 선택한 알고리즘의 참조 구현(공식 저장소)에서 가져온 입력·기대 출력. 출처 커밋·파일·라이선스를 테스트 파일 머리에 적는다. 부동소수는 허용 오차를 명시한다 |
| 성질 | 같은 상태에서 다시 < 어려움 ≤ 알맞음 ≤ 쉬움 간격, 알맞음을 연속하면 간격이 줄지 않음, 다음 기한 > 복습 시각, 최대 간격 넘지 않음 |
| 시간 | 학습일 경계 직전·직후, 시간대 변경, 서머타임이 있는 시간대, 연체·조기 복습 |
| 결정성 | 같은 입력 두 번 → 같은 결과, 상태 직렬화 왕복 |

참조 벡터를 기억으로 만들지 않는다. 참조 구현을 실제로 실행할 수 없으면 공식 저장소의 테스트 파일에 적힌 값만 쓰고, 그것도 없으면 그 사실을 보고하고 성질 테스트로 대신한다.

## 5. 저장(학습 기록 DB)

- 복습 로그는 추가만 한다: 카드 ID, 복습 시각, 평가, 이전·이후 상태, 경과 일수, `schedulerVersion`. 나중에 파라미터 최적화나 알고리즘 교체를 하려면 이 기록이 필요하다.
- 카드 상태 갱신과 로그 추가는 한 트랜잭션(`compose-app-dev` 5절).
- 되돌리기는 마지막 로그의 이전 상태를 복원하고 로그에 되돌림을 표시한다(삭제하지 않는다).

## 6. 리뷰에서 볼 것

- 시스템 시계 직접 호출, 시간대 하드코딩(`ZoneId.of("Asia/Seoul")`), 일 계산에 `Duration.toDays()`만 쓰는 코드(학습일 경계 무시).
- 참조 벡터 없이 "그럴듯한" 기대값을 손으로 적은 테스트.
- 평가 값과 화면 버튼의 대응이 한 곳에 정의되지 않은 코드.
